Apache Flink ve ksqlDB

Banking Fraud Lab’de ne yaptık, Flink’i neden ve nasıl kullandık, aynı problem ksqlDB ile nasıl ele alınırdı?

Bu projedeki yaklaşım Java DataStream API, keyed/broadcast state, event time, watermark, window, side output, checkpoint ve transactional Kafka sink.
Karşılaştırılan yaklaşım Kafka üzerinde SQL ile stream/table tanımları, persistent query, windowed aggregation ve materialized view.
Kısa sonuç: Bu laboratuvarın dinamik rule broadcast’i, özel dedup TTL’i, typed side output’ları ve ayrıntılı event-time kontrolü Flink’in güçlü olduğu alandır. ksqlDB; Kafka merkezli, SQL ile ifade edilebilen filtreleme, dönüşüm, join ve aggregation işlerinde daha az kodla daha hızlı sonuç verir.

Yönetici özeti

Bu proje, Kafka uyumlu Redpanda’ya yazılan banka işlemlerini sürekli okuyup dolandırıcılık sinyalleri üreten stateful bir Flink job’ıdır. Job yalnızca mesaj taşımaz; her transaction kimliğini 24 saat hatırlar, kuralları canlı olarak broadcast state’te günceller, işlem zamanına göre pencereler oluşturur ve sonuçları checkpoint ile koordineli Kafka transaction’larına yazar.

Flink’in kazandırdığı

  • Keyed ve broadcast state üzerinde doğrudan kontrol
  • Watermark, idleness, allowed lateness ve side output
  • Özel Java iş mantığı ve farklı rule stratejileri
  • Checkpoint/savepoint tabanlı state recovery
  • Kafka dışında başka source/sink’lere açılabilme

ksqlDB’nin kazandırdığı

  • Java job yazmadan SQL ile sürekli sorgular
  • Kafka STREAM/TABLE modeli ve kolay aggregation/join
  • Materialized view üzerinde pull query
  • Daha düşük uygulama kodu ve hızlı analitik geliştirme
  • Kafka-native operasyon modeli
Terminoloji: Kullanıcının “ksql” dediği ürünün güncel adı ksqlDB’dir. ksqlDB, Kafka Streams üzerinde çalışan bir SQL stream-processing katmanıdır; Kafka’nın yerine geçmez.

1. Problem: gerçek zamanlı banka fraud işleme

Girdi, sonsuz bir transaction akışıdır. Her kayıt; transaction ve hesap kimliği, minor-unit tutar, para birimi, ülke, kanal, durum ve olay zamanı taşır. Sistemden beklenen, kayıtları yalnızca sırayla tüketmek değil; bozuk veriyi ayırmak, tekrarları engellemek, güncellenebilir kuralları uygulamak ve zaman pencerelerinde davranış özeti çıkarmaktır.

  • Event’in işlendiği makine saatine değil, bankacılık olayının gerçekleşme zamanına göre sonuç üretmek.
  • Failure sonrası Kafka offset’i ile operator state’ini aynı tutarlı noktadan geri yüklemek.
  • Downstream consumer’a yarım Kafka transaction göstermemek.
  • Operator UID’lerini sabit tutarak stateful upgrade/savepoint yolunu açık bırakmak.
  • Invalid, duplicate ve late kayıtları kaybetmeden ayrı audit akışlarına yönlendirmek.
Para modeli: Tutarlar double yerine long amountMinor olarak tutulur. Örneğin 12500, TRY için 125,00 TL’yi ifade eder. Böylece floating-point yuvarlama hataları rule sınırını bozmaz.

Flink UI’da görülen fiziksel graph

Flink, ardışık ve uyumlu operator’leri operator chaining ile aynı vertex içinde çalıştırır. Canlı çalıştırmada yedi vertex, her vertex için parallelism 2 ve toplam 14 logical subtask görüldü. Slot sharing sayesinde bunlar 14 ayrı container veya 14 ayrı slot değildir.

  1. Kafka transactions → parse/validate → watermark → invalid sink
  2. Kafka fraud rules → rule parse
  3. 24h idempotency filter → duplicate sink
  4. Broadcast-state dynamic rule evaluation
  5. One-minute account risk window → summary/late sinks
  6. Sliding-window velocity detector
  7. Exactly-once fraud alert writer/committer
HASH / BROADCAST / FORWARD: keyBy bağlantıları HASH shuffle üretir; rule stream’i bütün evaluator subtasks’a BROADCAST edilir; aynı paralel kanal üzerinden devam eden akış FORWARD görünür.

3. Projede Flink’i nasıl kullandık?

3.1 Kaynak, parse ve typed side output

bank-transactions önce ham String olarak okunur. JSON → TransactionEvent dönüşümü ve validation tamamlanınca valid event ana stream’e, hatalı event OutputTag<RejectedEvent> üzerinden invalid side output’a gider. Böylece bozuk bir JSON bütün job’ı restart döngüsüne sokmaz.

3.2 Event time, watermark ve idleness

Timestamp doğrudan eventTimeEpochMillis alanından atanır. Bounded-out-of-orderness varsayılan 5 saniyedir. Watermark kabaca “gördüğüm en büyük event zamanı − 5 saniye” ilerler. Boş Kafka partition’ın ilerlemeyi durdurmaması için transaction stream’inde 5 saniyelik idleness bulunur.

3.3 Keyed state ile deduplication

Stream transactionId ile key edilir. Her key için ValueState<Boolean> tutulur. İlk event state’i yazar; sonraki aynı ID ana akıştan çıkar ve duplicate side output’a gider. 24 saatlik TTL processing time tabanlıdır; bu nedenle “event time’a göre tam 24 saat dedup” anlamına gelmez.

3.4 Broadcast state ile dinamik kurallar

fraud-rules stream’i MapStateDescriptor<String, RuleConfig> ile broadcast edilir. Transaction stream’i account ID ile keyed durumdayken iki stream KeyedBroadcastProcessFunction üzerinden birleşir. Rule update yalnız daha yüksek version ise state’e yazılır. Transaction tarafı state’i read-only görür ve bütün aktif stratejileri değerlendirir.

3.5 İki farklı event-time window

WindowAmaçState/çıktı davranışı
1 dakika tumblingAccount bazlı count, declined count, total ve max amountÇakışmaz; incremental accumulator + pencere metadata’sı
60 sn / 10 sn slidingKısa sürede çok sayıda işlem (velocity)Bir event altı pencereye girebilir; eşik aşılırsa alert

3.6 Side output’ların iş değeri

Invalid, duplicate, too-late ve rule alert akışları ana event tipini kirletmeden ayrı, typed kanallara çıkar. Bu yapı audit, replay ve operasyonel metrik için değerlidir. ksqlDB karşılaştırmasında bu nokta özellikle önemlidir: ksqlDB’de çoğunlukla her ayrım için ayrı persistent query kurulur.

4. Bir transaction’ın uçtan uca yolculuğu

{
  "transactionId": "tx-123",
  "accountId": "acc-102",
  "amountMinor": 8000,
  "currency": "TRY",
  "country": "US",
  "channel": "MOBILE",
  "status": "APPROVED",
  "eventTimeEpochMillis": 1794126986962
}
  1. Producer mesajı bank-transactions topic’ine account ID key’i ile yazar.
  2. KafkaSource mesajı okur; offset checkpoint mekanizmasına katılır.
  3. JSON parse edilir ve zorunlu alanlar validate edilir.
  4. Event timestamp atanır; record watermark üretimine katılır.
  5. keyBy(transactionId) network shuffle yapar; dedup state kontrol edilir.
  6. İlk kez görülüyorsa seen=true yazılır ve event devam eder.
  7. keyBy(accountId) sonrası event, rule broadcast stream’i ile bağlanır.
  8. Beklenen ülke TR iken event ülkesi US olduğundan COUNTRY_MISMATCH alert’i oluşur.
  9. Alert deterministik doğal anahtardan üretilen ID ile fraud-alert side output’una gider.
  10. Transaction risk ve velocity window’larına da aktarılır.
  11. Kafka sink mesajı açık transaction’a yazar; checkpoint başarılı olunca commit eder.
  12. read_committed consumer yalnız commit edilmiş alert’i görür.
Canlı testte doğrulananlar: COUNTRY_MISMATCH alert’i, boş account ID nedeniyle invalid-event ve ikinci kez gelen transaction nedeniyle duplicate-event üretildi. Checkpoint sayısı 30/30 başarılıydı; state yaklaşık 33 KB’den 39 KB’ye büyüdü.

Rule alert ID neden deterministik?

ID; ruleId + ruleVersion + transactionId doğal anahtarından üretilir. Failure/replay sonrasında aynı mantıksal alert yeniden hesaplanırsa aynı ID çıkar. Bu, downstream idempotent upsert veya dedup tasarımını kolaylaştırır.

5. Checkpoint, recovery ve exactly-once

Job her 10 saniyede bir exactly-once checkpoint başlatır. Aynı checkpoint barrier’ı aşağıdaki parçaları tutarlı bir snapshot’ta birleştirir:

  • Kafka source offset’leri
  • Dedup keyed state
  • Broadcast rule state
  • Risk ve velocity window accumulator state’i
  • Kafka sink transaction/committer durumu
Replayable
Kafka source
→
Checkpoint barrier
operator state
→
Kafka transaction
commit on checkpoint

Failure olduğunda

  1. JobManager son başarılı checkpoint’i seçer.
  2. Keyed/broadcast/window state geri yüklenir.
  3. Kafka source, checkpoint’te kayıtlı offset’ten replay eder.
  4. Tamamlanmamış sink transaction abort/fence edilir.
  5. Yeni output, sonraki başarılı checkpoint ile görünür olur.
Exactly-once’ın doğru yorumu: Java kodunun fiziksel olarak yalnız bir kez çalışması değildir. Failure sonrası event yeniden işlenebilir; amaç, yönetilen state ve transactional/idempotent sink sonucunun gözlemlenebilir biçimde bir kez etkilenmesidir.

6. Canlı testte yakalanan watermark problemi

Transaction source’unda watermark ve idleness doğru tanımlı olsa da rule source’u WatermarkStrategy.noWatermarks() kullanıyor. İki-input dynamic rule operator’ünde output watermark, aktif input watermark’larının minimumuna göre ilerlediği için rule tarafı tüm downstream event-time window’larını bloke etti.

Ölçülen metrik:
Transaction input watermark: 1794126993095
Rule input watermark: -9223372036854775808 (Long.MIN_VALUE)
Dynamic evaluator output watermark: -9223372036854775808

Sonuç olarak immediate yollar çalıştı; COUNTRY_MISMATCH, invalid ve duplicate topic’lerinde kayıt görüldü. Ancak aşağıdaki event-time sonuçları fire etmedi:

  • Bir dakikalık risk summary
  • Sliding-window velocity alert
  • Risk window too-late side output

Önerilen düzeltme yönü

Rule stream’i uzun süre veri üretmeyen bir control stream olduğundan idleness ile işaretlenmelidir. Kavramsal değişiklik:

WatermarkStrategy.<String>noWatermarks()
    .withIdleness(Duration.ofSeconds(5))

Bu yaklaşım, rule input sessizken onu watermark hesabında idle kabul eder ve transaction watermark’ının downstream’e geçmesine izin verir. Düzeltme; unit/integration test, Flink UI’daki input/output watermark metrikleri ve burst/late senaryolarıyla doğrulanmalıdır.

Ders: Tek bir source’un watermark’ının doğru ilerlemesi yeterli değildir. Join/connect gibi çok-input’lu operator’lerde en yavaş aktif input tüm event-time zincirini belirleyebilir. UI’daki currentInput1Watermark, currentInput2Watermark ve currentOutputWatermark birlikte izlenmelidir.

7. ksqlDB nedir ve çalışma modeli nasıldır?

ksqlDB, Kafka topic’lerinden stream-processing uygulamaları üretmek için SQL kullanan ve Kafka Streams üzerinde çalışan bir platformdur. Kullanıcı Java ile operator graph yazmak yerine STREAM/TABLE şemaları ve sürekli SQL sorguları tanımlar. ksqlDB bu sorguları fiziksel Kafka Streams topolojilerine dönüştürür.

Temel kavramlar

KavramAnlamı
STREAMDeğişmez event dizisi; tipik olarak Kafka topic’inin schema’lı görünümü
TABLEKey başına güncel değer/changelog semantiği; materialized state
Persistent queryCREATE STREAM/TABLE AS SELECT; sürekli çalışır ve output topic üretir
Push queryUzun yaşayan bağlantıyla değişen sonuçları istemciye iter; sonucu topic’e kalıcı yazmaz
Pull queryMaterialized view’ın mevcut durumunu request/response şeklinde okur
Window + graceKey bazlı zaman penceresi ve out-of-order kayıt için kabul süresi

ksqlDB uygulama yaşam döngüsü

  1. Kafka topic, CREATE STREAM veya CREATE TABLE ile kaydedilir.
  2. İş mantığı SQL ile tanımlanır.
  3. ksqlDB sorguyu parse eder ve logical/physical plan üretir.
  4. Kafka Streams topolojisi oluşturulur ve ksqlDB server’larında çalışır.
  5. State store’lar ve internal/repartition/changelog topic’leri Kafka Streams tarafından yönetilir.

Processing guarantee

ksqlDB’de varsayılan garanti at-least-once’dur. Exactly-once için processing.guarantee="exactly_once_v2" ayarlanmalıdır. Uçtan uca sonuç yine producer/consumer ve dış sistemlerin semantiğine bağlıdır.

9. Bu proje ksqlDB ile nasıl görünürdü?

Aşağıdaki SQL bir üretim çözümü değil, yaklaşımı göstermek için sadeleştirilmiş taslaktır. Alan adları ve format ayarları gerçek schema contract’ına göre uyarlanmalıdır.

Transaction stream’ini kaydetme

CREATE STREAM BANK_TRANSACTIONS (
  TRANSACTION_ID STRING,
  ACCOUNT_ID STRING,
  AMOUNT_MINOR BIGINT,
  CURRENCY STRING,
  COUNTRY STRING,
  CHANNEL STRING,
  STATUS STRING,
  EVENT_TIME_EPOCH_MILLIS BIGINT
) WITH (
  KAFKA_TOPIC='bank-transactions',
  VALUE_FORMAT='JSON',
  TIMESTAMP='EVENT_TIME_EPOCH_MILLIS'
);

Valid event akışı

CREATE STREAM VALID_TRANSACTIONS AS
SELECT *
FROM BANK_TRANSACTIONS
WHERE TRANSACTION_ID IS NOT NULL
  AND ACCOUNT_ID IS NOT NULL
  AND AMOUNT_MINOR > 0
  AND CURRENCY IN ('TRY', 'USD', 'EUR', 'GBP')
EMIT CHANGES;

Bir dakikalık risk materialization

CREATE TABLE ACCOUNT_RISK_1M AS
SELECT
  ACCOUNT_ID,
  COUNT(*) AS TRANSACTION_COUNT,
  SUM(CASE WHEN STATUS = 'DECLINED' THEN 1 ELSE 0 END) AS DECLINED_COUNT,
  SUM(AMOUNT_MINOR) AS TOTAL_AMOUNT_MINOR,
  MAX(AMOUNT_MINOR) AS MAX_AMOUNT_MINOR
FROM VALID_TRANSACTIONS
WINDOW TUMBLING (SIZE 1 MINUTE, GRACE PERIOD 30 SECONDS)
GROUP BY ACCOUNT_ID
EMIT CHANGES;

60 saniyelik velocity

CREATE TABLE ACCOUNT_VELOCITY_60S AS
SELECT ACCOUNT_ID, COUNT(*) AS TX_COUNT, SUM(AMOUNT_MINOR) AS TOTAL_AMOUNT
FROM VALID_TRANSACTIONS
WINDOW HOPPING (SIZE 60 SECONDS, ADVANCE BY 10 SECONDS,
                GRACE PERIOD 30 SECONDS)
GROUP BY ACCOUNT_ID
HAVING COUNT(*) >= 5
EMIT CHANGES;

Bu sorgular, window aggregation tarafında ksqlDB’nin ne kadar kısa ve okunabilir olabileceğini gösterir. Buna karşılık mevcut Flink çözümündeki typed invalid raw payload, 24 saatlik “ilk event’i geçir” dedup state’i, rule factory/strategy ve late side output için ek query/topology tasarımı gerekir.

Dinamik rule join’inde kritik semantik

ksqlDB stream-table join’de yeni stream kaydı geldiğinde table’ın o anki değeriyle lookup yapılır. Table tarafındaki sonraki update, geçmiş stream kayıtlarını otomatik olarak yeniden değerlendirmez. Bu projedeki Flink davranışı da geçmiş event’leri yeniden yürütmüyor; ancak broadcast state ve özel evaluator, farklı rule türleri ve state erişimi üzerinde daha fazla kontrol sağlıyor.

Temporal rule ihtiyacı: Mevcut Flink uygulaması da yalnız en yeni rule version’ını saklar. Geç event’in olay zamanında geçerli eski rule version’ıyla değerlendirilmesi gerekiyorsa her iki teknolojide de versioned/temporal rule tasarımı gerekir.

11. Hangi durumda hangisini seçmeliyiz?

Flink’i seç

  • Özel state machine, timer veya CEP gerekiyorsa
  • Watermark ve geç veri yönlendirmesinde ayrıntılı kontrol gerekiyorsa
  • Kafka dışında CDC, object storage, database veya başka source/sink’ler varsa
  • Dinamik kural motoru, async enrichment veya özel retry semantiği varsa
  • Büyük state ve uzun yaşayan karmaşık job’lar yönetilecekse

ksqlDB’yi seç

  • Veri Kafka’da ve sonuç yine Kafka’ya gidecekse
  • İş mantığı SELECT/FILTER/JOIN/GROUP BY/WINDOW ile doğal ifade ediliyorsa
  • SQL bilen ekip hızlı teslim yapmak istiyorsa
  • Materialized view’a pull query ihtiyacı varsa
  • Özel operator state/timer yerine engine-managed state yeterliyse

Bu proje için karar

Öğrenme ve ileri seviye fraud motoru hedefi açısından Flink doğru seçimdir. Çünkü projenin öğretmek istediği ana konular keyed state, broadcast state, watermark, allowed lateness, typed side output, checkpoint ve stateful recovery’dir. Bunlar Flink’in programlanabilir çekirdeğini doğrudan gösterir.

Buna karşılık yalnızca “bir dakikadaki toplam tutarı ve işlem sayısını Kafka topic’ine yaz” ihtiyacı olsaydı ksqlDB daha ekonomik çözüm olurdu. Java JAR, custom accumulator ve window function yazmadan kısa SQL ile aynı aggregate üretilebilirdi.

Hibrit yaklaşım

Teknolojiler birbirini dışlamak zorunda değildir:

  • Flink karmaşık fraud kararlarını, dedup ve dynamic rule state’ini çalıştırabilir.
  • Flink sonuçları Kafka topic’lerine yazabilir.
  • ksqlDB alert topic’lerini SQL ile dashboard/operasyon görünümlerine dönüştürebilir.
  • ksqlDB materialized TABLE üzerinden düşük gecikmeli pull query sunabilir.
Pratik karar cümlesi: “SQL ile doğal ve tamamen Kafka-merkezli ise önce ksqlDB; özel state/time/control-flow gerekiyorsa Flink.”

12. Görüşme için kısa cevaplar

“Flink ile bu projede tam olarak ne yaptınız?”

Kafka’dan banka işlemleri ve dinamik kurallar okuyan stateful bir DataStream job’ı kurduk. Event timestamp’lerinden bounded-out-of-orderness watermark ürettik; transaction ID bazlı TTL’li keyed state ile dedup yaptık; rule topic’ini broadcast state’e alıp account-keyed event’lerle bağladık. Bir dakikalık tumbling risk özeti ve 60/10 saniyelik sliding velocity detector oluşturduk. Invalid, duplicate, rule alert ve late kayıtları typed side output’lara ayırdık. Kafka output’larını checkpoint ile koordineli exactly-once transaction’lara yazdık.

“Neden ksqlDB değil?”

ksqlDB window aggregation ve basit join’lerde daha az kod isterdi. Ancak özel TTL’li dedup, heterojen rule stratejileri, broadcast state, typed side output ve watermark/idleness kontrolü bu projenin ana hedefiydi. Bu nedenle Flink daha uygun ve öğretici oldu.

“Exactly-once gerçekten her kod satırı bir kez mi çalışıyor?”

Hayır. Failure sonrası event replay edilip kod yeniden çalışabilir. Exactly-once; state snapshot’ı, source offset’i ve destekleyen transactional/idempotent sink’in gözlemlenebilir sonucunun tutarlı olmasını ifade eder.

“Watermark neden gerekli?”

Unbounded stream’de event-time penceresinin tamamlandığına karar verecek doğal bir “son kayıt” yoktur. Watermark, sistemin hangi olay zamanına kadar büyük ölçüde tamamlandığı iddiasıdır; latency ile completeness arasındaki iş kararını kodlar.

“Canlı testte ne öğrendiniz?”

Çok-input’lu operator’de tek bir no-watermark control stream’inin bütün downstream window’ları bloke edebileceğini gördük. Transaction watermark ilerlerken rule input Long.MIN_VALUE kaldı. Bu, idleness’in yalnız Kafka partition’larında değil, bağlı control stream’lerinde de düşünülmesi gerektiğini gösterdi.
